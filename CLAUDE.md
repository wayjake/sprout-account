# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Sprout Account — Household Ledger** — a local-only household finance manager (React Router + SQLite, no accounts, no cloud) dressed in 1999 desktop-software chrome. It imports bank/card statements, categorizes spending into base/living/luxury classes, tracks investment balances, and matches Amazon orders to card charges. It ships both as a dev web app and as a compiled macOS desktop app. See `README.md` for the user-facing feature tour.

## Commands

```sh
npm run dev              # dev server (Bun-driven; user usually has this running already)
npm run typecheck        # react-router typegen && tsc — the only automated check in the repo
npm run db:push          # sync app/db/schema.ts → SQLite (use this, not migrations)
npm run db:studio        # browse the database
npm run seed             # idempotent starter categories
npm run seed -- --fake 12000   # + generated fake transactions for pagination/perf work
npm run test:extraction  # real statement fixtures through the real extraction path (needs OPENROUTER_API_KEY, spends AI credit)
npm run build            # react-router build
npm run desktop:build    # web build → Bun binary → Tauri .app/.dmg (needs rustup + sqlite3)
```

There is no unit test suite and no linter. `npm run typecheck` is the routine verification step; it runs `react-router typegen` first, so route type errors after adding a route usually just mean typegen hasn't run. The one real test is `npm run test:extraction` (`scripts/test-extraction.ts`): it runs the checked-in statement fixtures in `scripts/fixtures/` through the genuine chunked extraction path with the real model — each fixture is kept because it broke extraction in a distinct way, and the circumstances are documented at the top of the script. It needs `OPENROUTER_API_KEY`, costs real API calls, and exits non-zero if any statement would be held. `npm run test:extraction -- <file.pdf> [accountType]` checks a single statement (type defaults to `credit_card`); `--dump` writes the extraction JSON for inspection. Run it when touching `pdf.ts`, `pdf-split.ts` or `pdf-text.ts`.

`.env` knobs: `OPENROUTER_API_KEY`, `DATABASE_PATH` (default `./data/finance.db`), and **two** models — `OPENROUTER_MODEL` for categorization + CSV mapping, `OPENROUTER_MODEL_PDF` for statement extraction (a cheap model is fine for the first, not for the second). `TURSO_DB_URL` / `TURSO_DB_KEY` are optional — see the Bun/libSQL constraint below.

To start over: delete `data/finance.db*`, then `npm run db:push && npm run seed`.

## Runtime constraints

- **`app/.server/db.ts` runs on `@libsql/client` + `drizzle-orm/libsql`**, not `bun:sqlite` — a plain Node runtime can open it. `TURSO_DB_URL` / `TURSO_DB_KEY` unset means a plain local libSQL file, no network; set both and the local file becomes an embedded replica of a Turso primary — reads stay local, **writes delegate to Turso synchronously**, so a loop of per-row inserts (`commitBatch` in `stage.ts`) gets one network round trip per row once Turso is configured. Embedded replicas require a **classic (non-MVCC) Turso database** — `turso db create` without `--tursodb`; MVCC-mode databases can't sync this way (`SQLITE_NOTADB` on `client.sync()`) and only work as a pure-remote client. `scripts/desktop/server.ts` still uses `bun:sqlite` directly for its own first-run local bootstrap when Turso isn't configured — that path is unaffected.
- **React Router v8, framework mode, SSR on.** Every new route or renamed route file must be registered in `app/routes.ts`.
- **`app/.server/` is server-only** by React Router convention — anything imported from a route module's `loader`/`action` and nothing else. Code shared with the browser (money parsing, CSV mapping preview, date math) lives in `app/lib/` and must stay isomorphic.
- Schema changes go through `npm run db:push`. The `drizzle/` migrations folder is configured but deliberately unused for now. **`drizzle-kit` (0.31) cannot round-trip a partial index**: it reads `txn_transfer_target_idx`'s `where` clause back as different from what it wrote, so every push drops and recreates it. That is ~6ms and harmless, but it means push is never a clean no-op — read past that one pair of statements when checking whether a push is about to do something you didn't intend. No spelling of the predicate avoids it (bare, double-quoted and backtick-quoted were all measured).
- `.agents/skills/react-router/` holds a vendored React Router skill with per-mode reference docs — read `references/framework-mode.md` (this app's mode) before guessing at router API behaviour.

## Data model invariants

`app/db/schema.ts` is the single source of truth; these rules are assumed everywhere downstream:

- **Money is integer cents, never floats.** Parse user/CSV/AI decimal strings with `parseCentsString` (`app/lib/money.ts`) — even AI PDF extraction returns amount *strings* for this reason.
- **Signs are household perspective**: spending negative, income positive; assets positive, debts negative. `isLiability` (`app/lib/accounts.ts`) is the single list of debt types — `credit_card`, `line_of_credit`, `mortgage`, `loan`. Never special-case `credit_card` directly; anything true of a card is true of the other three.
- **A positive amount on a debt is never income.** It is a payment or a credit coming off what is owed. `guardLiabilityCredit` (`app/.server/categorize.ts`) enforces this deterministically ahead of both the memory and the AI pass, because transfer matching can only catch it when the funding account's leg was imported too.
- **An account's `kind` is derived from its type, except for debts.** Loans ask: a line of credit usually has a statement worth importing row by row, a mortgage usually just a principal balance. `supportsKindChoice` / `resolveAccountKind` (`app/lib/accounts.ts`) own that rule, and `settings.accounts.ts` refuses to switch an account to balance-only while it still holds transactions.
- **Dates are ISO `YYYY-MM-DD` strings**, compared and sorted lexically; all date math goes through `app/lib/dates.ts` in UTC.
- `transactions.merchant` is the output of `normalizeMerchant` (`app/.server/categorize.ts`) — the key for merchant memory. Changing that function changes what matches historical memory, so re-key existing rows when you touch it. It is *not* a dedupe input: `computeTxnHashes` uses its own `normalizeDescription` (`app/.server/import/stage.ts`), so the two can change independently.
- Dedupe is per-account: `uniqueIndex(accountId, dedupeHash)`, where the hash is `date|amount|normalized description|occurrence-ordinal-within-file`. The statement path hashes through the same `computeTxnHashes`, so the ordinal is there too — without it, two identical charges on one day would collapse into one insert and the statement would stop tying out to the anchor it recorded in the same breath.
- **An account learns its own number.** `matchAccountByHint`'s strongest branch tests `lastFour`, so an account without one can never match it — which is why its statements have to be reassigned by hand, every month. `reassignBatch` backfills `accounts.lastFour` from what the statement printed, but only into a blank: a shared statement or a reissued card would otherwise rewrite the account's identity and orphan every match made before it. What the statement printed is kept in the batch's `statsJson.identity` for exactly this, and for filling in the "create the account from this statement" offer.
- **Household-level only** — there is no per-person account/transaction concept, and it should not be reintroduced.

## Architecture

**Three upload flows, one pipeline.** CSV transaction exports and PDF statements answer different questions, so they have separate screens and never mix in one session. `import_sessions.purpose` (`import` / `reconcile` / `bulk`) records which flow a session belongs to, and the session review screens redirect to the right one when the purpose doesn't match. Everything below the routes — batches, staged rows, commit, categorize — is shared.

- **`/import` — Transaction Import (CSV only).** Exports are the source of the register. A PDF here is refused with a pointer to `/reconcile`, and the whole upload is rejected rather than half of it, because a wrong file type is a mistake about which screen you're on.
- **`/reconcile` — Monthly Reconcile (PDF only).** A statement is *both* the authority the ledger gets checked against and, for the lines the ledger turns out to lack, a source of them. Its balances become anchors and its lines are matched against the books; the unmatched ones are the gap, and adding them is a first-class outcome rather than a fallback. (This reverses an earlier stance that a statement was never a source of transactions. It was always half untrue — the close has always offered the missing lines — and it made bootstrapping a ledger from statements impossible for anyone without years of CSV exports.)
- **`/import/bulk` — Bulk Statement Import (PDF only, beta).** The close's machinery run unattended over a whole folder. On an account with no ledger the statements *become* the ledger; on one that already has rows, only the gaps are added. Same code path either way, which is what makes re-running a growing folder safe.

**Import pipeline** (`app/.server/import/`) — the most intricate flow. One upload = one `import_session` containing N `import_batches`; nothing touches `transactions` until commit.

1. `intake.ts` has one entry point per flow — `intakeTransactions` (CSV) and `intakeStatement` (PDF) — sharing account resolution: guess from the filename, then let a statement's printed account number overrule it. Neither throws per-file (a bad file returns an error result and the rest proceed).
2. PDFs → `pdf.ts` (AI extraction of transactions *and* bracketing balances). CSVs → a per-account saved column mapping keyed by header signature (`mapping.ts`, AI-suggested once with a header-name heuristic fallback, then reused); unmapped CSVs stop at status `mapping` and wait for the user.
3. `stage.ts` writes `staged_rows` with a per-row status (`new` / `duplicate` / `possible_duplicate` / `excluded`), detects re-imports by file hash and overlapping statement periods, and can re-stage a batch against a different account (dedupe is account-relative, so everything is re-derived — including the ledger match, which is why `restageBatchAccount` looks the session purpose back up).
4. `commitBatch` inserts inside a single `db.transaction`, auto-categorizes from merchant memory, records balance snapshots, deletes the staged rows, and optionally auto-links transfers.
5. Commit redirects to the **register**, not to a screen of its own: `importedRegisterSearch` (`queries.ts`) turns the committed batches into `/transactions?account=&from=&to=&category=none`, so you land on exactly what the import added that still needs filing, and file it in the transaction window like any other row. The account survives only when the session touched exactly one, since the register filters on a single id. Skipped when nothing was inserted, which is the usual outcome of a clean close. The commit counts ride along in the query string because they only exist in memory at that point — per-batch `statsJson` has no session-wide transfer count — so a revisit simply shows no banner. There was a dedicated post-import categorize screen here once; it was removed because it was a second, worse register.

Raw uploads are kept in `data/uploads/<owner>-<id>` between steps and deleted on commit/discard — `batch-` for a CSV waiting on its column mapping, `bulk-` for a statement a bulk run has not read yet (a bulk file exists before any batch does, so it needs a key of its own).

**The bulk run** (`app/.server/import/bulk.ts`, `routes/bulk-*.tsx`, `routes/api.bulk-step.ts`) is the close's pipeline with the waiting taken out of the request. A folder is uploaded, written to disk, and a `bulk_files` row per statement records where it has got to; **nothing is read during the upload**, which is what makes the run resumable. From there the browser drives it, `POST /api/bulk/step` at a time, the same pattern and for the same reasons as `components/categorize-run.tsx` — progress lands in the page as each statement finishes, and a pause takes effect between steps. Closing the tab pauses the run; every step wrote what it did before returning, so Resume carries on from the next file.

**One step per run at a time**, enforced on the server (`stepsInFlight` in `bulk.ts`), not by trusting the client. A step picks the next file by its status and only writes that status back when the work is done, so two overlapping steps pick the *same* file and both extract it — two AI passes over one statement and a duplicate batch whose rows dedupe away to nothing. That is not hypothetical: it happened on the first folder ever run, to every statement in it. A second caller now rides along with the step already going.

The phases are `scan → dedupe → commit → categorize`, and **the order is load-bearing: nothing commits until every file has staged.** `dedupeSessionBatches` decides which of several overlapping statements owns a row and can only choose once they are all in front of it; committing file by file would put statement N's rows in the ledger before statement N+1 stages, leaving overlap resolution to fall back on ordinary dedupe, and two statements covering the same fortnight would import it twice. `scan` itself is two steps interleaved — identify (`identify.ts`, three files at once, one small AI call against page 1 each) then extract (one file, since `extractFromPdf` already fans its own pages out). Identification is concurrent but **account creation is not**: settling accounts one at a time, appending each new one to the list, is what stops twelve monthly statements for one new account from creating twelve accounts.

**Settling a statement's account goes match → folder consensus → ask → create, and creating is last for a reason.** `resolveStatementAccount` reports a *tie* rather than swallowing it (`matchAccountsByHint`), because nothing-matched and everything-matched call for opposite responses: the answer to a tie is one of the accounts already on file, so adding another only makes the tie worse. Failing that, the folder decides — a folder of statements is one account's statements far more often than not, so a file whose neighbours *unanimously* settled on one account joins them; two accounts in a folder means no consensus and a question. A run only creates an account when the statement actually printed a name or a number to create it from. All three rules come from one incident: six Apple Card statements where the AI read five as "Goldman Sachs / Apple Card" and the sixth as "Apple Card" with no name, which tied against two unrelated `Apple` accounts, matched nothing, and became a seventh account named after its own type — "Credit card", a label that would never have matched its own next statement either. The printed account holder is bound by the same logic from the other direction: it only chooses among accounts another probe already implicated (confirming a lone institution hit, breaking a tie), never on its own — nearly every statement in a household is addressed to the same person, and a holder allowed to act alone filed a folder of Robinhood statements under "Jake's Apple Card", the one account with the holder's name in it.

Two things stop a file mid-run. A **question** (`bulk_files.questionJson`, a closed set: which account, create this one, or this exact statement was imported before) parks the file at `needs_input` and the driver refuses to advance past `scan` while any are outstanding — a statement filed against the wrong account is harder to undo than to answer. A **hold** (`held`) stages the file but keeps it out of the automatic commit, and applies whether or not auto-commit is on: `PdfExtractionResult.blocked` (the rows don't tie out to the printed balances, or some fall outside the period) or an anchor that contradicts one already recorded for that date. The second is why `buildBalanceRows`' `possible_duplicate` status matters here — a month's closing anchor and the next month's opening one land on the same date by design, so agreement is the ordinary case and a disagreement means one of the two extractions is wrong. Held files link to `/reconcile/:sessionId`, which accepts `bulk` sessions as well as `reconcile` ones for exactly this reason; `closeHistory` stays filtered to `reconcile`, because a five-year bootstrap is not a month-end close.

**PDF extraction is chunked** (`pdf-split.ts` + `extractFromPdf` in `pdf.ts`) because the failure mode of a long statement is *silent truncation of output rows*, not an error — measured on a 22-page statement, whole-file extraction dropped up to 126 rows. Over `SPLIT_ABOVE_PAGES` (6), the file is cut into contiguous `CHUNK_PAGES` (3) page ranges — the budget is really *rows*, pages are a proxy; don't raise these without re-measuring — extracted concurrently (`mapWithConcurrency`, one request per chunk), and folded back into one result by `mergeRaw`, where first-chunk-wins for period/balances/account number so a running total on a later page can't displace the printed figure. A PDF too damaged for `pdf-lib` to parse falls back to whole-file extraction rather than failing the upload. Two checks run on the merged result and surface as `problems` on the close screen rather than retrying — every observed tie-out failure was structural (mis-signed returns), so a second pass just doubles the cost: the printed lines must net to exactly the distance between the printed opening and closing balances, and no row may fall outside `(opening, closing]`. The one retry that isn't a dice roll is deterministic: when the merged result is blocked — or has no period or anchors, which only looks clean because there's nothing left to check against — `auditTransactionsFromText` (`pdf-text.ts`) parses the PDF's own text layer (`signed` layout for liabilities, `columnar` for banks, where the AI loses track of which column an unsigned figure sat in) and its rows replace the AI's only when they explain the printed balance movement to the cent. A failed or impossible audit (scanned PDF, unrecognised layout, parse that sums wrong) changes nothing, so the pass can only turn a held statement into a clean one, never the reverse. `npm run test:extraction` exists to protect exactly this machinery. Rows falling short of the period (transaction-dated lines a posting-dated opening balance rightly excludes) are *clamped* forward to the day after the opening anchor, with the printed date preserved as `matchDate` — which `stage.ts` matches the ledger on instead of the filed date, and persists in staged data so a re-stage against another account still matches on what the statement said.

**The close** (`app/.server/reconcile.ts`, `routes/reconcile*.tsx`) inverts what staging means for a statement. `stageBatchRows({ matchLedger: true })` runs `buildStatementTransactionRows` instead of the import's dedupe: each line is matched one-to-one against rows already in that account on amount plus a date within `STATEMENT_MATCH_WINDOW_DAYS`, **never on description** — a statement prints "Coffee Shop" where the export said "SQ *COFFEE 1234". Matching runs in widening passes (exact date first, then a day out, then two) so a near miss can't steal the exact match belonging to another line, and a consumed ledger row is off the table, so two identical charges on one day need two ledger rows to both come back matched. A matched line stages as `duplicate` carrying `duplicateOfId`; an unmatched one stages as `new` and is the gap the close offers to fill. **A line whose only counterpart is the exact opposite amount is a sign conflict, not a gap** — an incoming transfer the extractor read as outgoing. It stages as `duplicate` with `signConflict`, because adding it would insert a second wrong-signed copy and throw the period off by *twice* the amount, and `diagnose` would then blame a double import that never happened. That pass runs only after every exact pass, so it can never take a row some line matches outright, and sign conflicts are counted separately from matched lines so a real disagreement can't hide inside an all-clear tally. The user can force a matched line in ("add anyway") or skip a missing one — both are just the existing include/exclude toggle. `ReconcilePanel` on the close screen runs `pendingRowsForBatches` through `reconcileAccounts`, so the preview is the arithmetic of the commit that hasn't happened yet.

**Categorization** (`app/.server/categorize.ts`) is layered, and the layering is the point: far-side account links first (`autoLinkAccountTransfers`, pass 0 — a link decides the category itself, so it must not be second-guessed by memory), then the deterministic `guardLiabilityCredit` rule, then merchant memory (free, no network), then AI for what's left, in batches, with a confidence floor. `categorySource` (`user` / `memory` / `ai` / `auto`) records which layer won — `auto` is the rule pass. The guard also *vetoes*: when memory or the AI proposes an income category for a credit on a debt account, the row is left uncategorized (counted as `blocked`) rather than mis-filed, and the AI's answer never reaches merchant memory. `recordUserChoice` overwrites anything; `recordAiChoice` never overwrites a `user`-sourced memory row.

**The bulk run is client-driven** (`components/categorize-run.tsx` → `api/ai/categorize`). The endpoint answers `intent=plan` with the id list for the whole run and `intent=run` with one chunk's stats, and the client posts one chunk (`AI_BATCH_SIZE`, so one AI call) per fetcher submission. Each submission revalidates the page's loaders, so rows fill in as they are decided instead of after a single minutes-long request, and the chunk boundary is where Cancel takes effect — the chunk in flight is already paid for and still finishes. **The client owns the id list** because the layers deliberately leave rows uncategorized (low confidence, guard-blocked): a server-side "next N uncategorized" loop would hand back the same rows forever.

**Balances** (`app/.server/balances.ts`) are derived, not stored: latest anchor (`balance_snapshots`) + transaction activity since it. With no anchor the figure is a *change* in balance, flagged `unanchored`. `reconcileAccounts` compares statement anchors against recorded activity and produces named, most-specific-first explanations for gaps. An explanation that can name the rows it is about carries a `link` built by `rowsLink` — `/transactions?ids=…`, an extra register filter that exists for exactly this, since a diagnosis that names a row and leaves you to hunt for it isn't much of a diagnosis. Rows an import is only previewing have no id yet, so they simply drop out of the link. `pendingRowsForBatches` feeds not-yet-committed rows through the same maths so both the import and close screens preview the outcome.

**Cleared state is derived too.** `transactions` has no reconciled column. `clearedWindows` returns each transaction-kind account's checked periods and `clearedStateFor` places a row in one: `reconciled` inside a period that ties out, `mismatch` inside one that doesn't, `open` outside every period (before the first anchor or after the last). This means editing a row correctly un-reconciles its whole period instead of leaving a stale flag. The window maths is duplicated from `reconcileAccounts` — same `(previous anchor, this anchor]` span, same `expected = from + activity`, same zero-diff test — because the register calls it on every page load and can't afford to read whole transactions; **if you change one, change both**, or a row will claim to be reconciled while the account screen says the period is off. The `?reconciled=yes|no` filter compiles the same windows into a SQL predicate rather than filtering the page, since filtering after pagination would return short pages and a cursor that skips rows.

Balance-only accounts reconcile on a different axis, and the distinction matters: they have no ledger to check a statement against, so their windows measure consecutive snapshots against the *contributions* pointed at them via `transferAccountId` (sign-flipped into that account's perspective). Whatever the contributions don't explain is market return on an asset, or accrued interest on a debt — reported as window status `movement` with a plain-language `note`, never as a `mismatch`, and a balance account's overall status therefore stays `ok`. This is what lets a $1,600 mortgage payment show up as $400 principal and $1,200 interest without the loan needing a ledger of its own.

**Transfers** (`app/.server/transfers.ts`) pair opposite-amount legs across accounts within `TRANSFER_WINDOW_DAYS`, greedy one-to-one by date proximity. Only mutually-unambiguous, transfer-looking pairs auto-link; the rest are suggestions. Linked legs get a transfer-class category so they drop out of income/spend reporting — `Credit Card Payment` when a card is involved, `Loan Payment` for other debts, else `Transfer` (`paymentCategoryName`). Dismissals persist in `transfer_rejections`.

The automatic window is a guess, so the transaction detail page also offers a manual picker: choose any active account and name the far side yourself. `manualPeerCandidates` (`MANUAL_TRANSFER_WINDOW_DAYS`, 60) drops the guardrails that only make sense for a guess — the tight date window, the "still uncategorized" filter, past dismissals — and a hand-made link clears the matching `transfer_rejections` row so unlinking later doesn't leave the pair permanently un-suggestable. **Equal-and-opposite is not one of the guardrails; it is the invariant.** `linkTransferPair` drops *both* legs out of reporting, so pairing −500 with +480 would make $20 vanish with no trace; the picker lists only opposite-amount rows and says which amount it looked for when an account has none.

On a transaction-tracked debt the payment splits in two: the principal leg links away as `Loan Payment` (transfer class, out of reporting) and the posted interest charge stands on its own as `Interest` (base class) — that separation is why both starter categories exist, and why interest is the only part of the payment that counts as spending.

**A balance-only account never produces an opposite row**, so pairing is structurally impossible there — `rawCandidatePairs` joins transactions to transactions. Those legs instead name the far *account*: `transactions.transferAccountId` (mutually exclusive with `transferPeerId`), set by `linkTransferToAccount`, which refuses any target that is not an active balance-kind account — **not a restriction to relax**: `reconcileAccounts` folds every `transferAccountId` leg in as a contribution to the account it names, so pointing one at an account that keeps its own ledger would count the movement twice, once as the contribution and once as the row itself. An account with a ledger isn't missing a row; its correct link is peer-to-peer. The leg gets a transfer-class category through the same `transferCategoryId` path as a pair, so it leaves income/spend reporting and stops showing up in `unmatchedTransferLegs`. Both link kinds count toward `transferVolume`.

**These links are found automatically too, at a deliberately high bar.** `autoLinkAccountTransfers` runs after `autoLinkTransfers` on every commit and as pass 0 of categorization (scoped by `ids`, or the register's chunked run would re-sweep the whole ledger 25 times). It links when the description names the account by its **last four or its name** *and* `looksLikeTransfer` — or when every earlier row in the same account with the same merchant already points at one target, which is a query over `transactions` rather than a second memory table that could drift out of step with it. **The `institution` branch of `matchAccountByHint` is excluded on purpose** (hence the `strength` field on its return value): "FIDELITY" appears on a brokerage *fee* as readily as on a contribution, and a wrong link both hides the row from reporting and folds it into the target's contributions, which is what separates market movement from money paid in. Everything below the bar is a suggestion on `/transfers`, never a link. The AI pass may also name a `transferAccountId`, held to the same confidence floor and to ids that really are active balance accounts.

Because the far side is an account rather than a row, deleting or re-kinding that account has to be blocked while legs point at it — `settings.accounts.ts` guards both directions (it already refused balance-only for an account holding transactions; it now also refuses transaction-kind for one that is somebody's named far side).

**Amazon** (`app/.server/amazon.ts`) matches orders to charges in three passes: exact 1:1, split shipments (one order, ≤4 charges), combined charges (≤3 orders, one charge); ambiguity goes to review. `applyItemSplits` pro-rates tax/shipping with largest-remainder rounding so splits sum exactly to the transaction.

**AI calls** all go through `chatJSON` (`app/.server/openrouter.ts`): OpenRouter, strict JSON-schema response format derived from a zod schema, one validation retry. Requests carry a timeout (`OPENROUTER_TIMEOUT_MS`, default 180s — chunked extraction means one stalled socket would otherwise hang a whole import) and up to three attempts on timeouts, dropped connections and the retryable statuses, honouring `Retry-After`. Every feature must degrade gracefully without `OPENROUTER_API_KEY` — PDF import is the only hard dependency.

**Backups** (`app/.server/backups.ts`) use `VACUUM INTO` for online snapshots into `data/backups/<timestamp>__<label>.db` — a local-file operation, unaffected by whether Turso is configured. **Restore does not file-swap.** Under an embedded replica the local file carries replication metadata tied to the primary, so overwriting it would desync rather than restore; instead `restoreBackup` opens the backup as its own standalone local db, reads every table (`DATA_TABLES`) out of it, and wipes + reloads the live tables through the normal write path in one transaction. `PRAGMA defer_foreign_keys = ON` inside that transaction is what lets every table — including the self-referencing `transactions.transferPeerId` — delete and reinsert in any order without a hand-computed FK sequence; `clearDatabase` uses the same pragma and the same `DATA_TABLES` list — **any new table holding household data has to be added to it**, or a restore will leave the old rows behind. Restore and reset are both slower than before when Turso is live, since every row is a network write.

**Rules export/import** (`app/.server/rules.ts`) is the seam between the two kinds of data the app holds: the ledger belongs to one household's file, while the categories and merchant memory are accumulated judgement worth keeping across a `clearDatabase()`. Everything in the file is keyed **by name**, never by id, because ids don't survive the wipe the feature exists to serve. The envelope carries a `merchantKeyFingerprint` — a hash of fixed probe descriptions run through `normalizeMerchant` — since a file's keys are only meaningful to a build that normalizes the same way; a mismatch warns rather than refuses, and **the probe list must not be edited** or every existing file starts looking stale. Import mirrors the live precedence (`recordUserChoice` / `recordAiChoice`): an incoming `ai` row never overwrites a local `user` one, `useCount` resolves to `max` not the sum, and rows resolving to what's already stored are skipped, so re-importing the same file is a genuine no-op. Categories are always merged and never deleted — an existing name keeps its local `spendingClass` (a rules file shouldn't silently reclassify Groceries) and deleting would orphan `transactions.categoryId` on a database that turned out not to be empty; `mode=replace` therefore scopes to merchant memory only. Writes are chunked multi-row upserts rather than a per-row loop, for the Turso round-trip reason. Export is a loader-only resource route (`routes/api.rules-export.ts`) whose response *is* the file; import is an intent on the Backups screen, which already has the multipart plumbing.

**Desktop** (`scripts/desktop/`, `src-tauri/`) — `build.ts` generates an embedded asset manifest, dumps the schema to `schema.generated.sql`, `bun build --compile`s `server.ts` to a single arm64 binary, and copies it as a Tauri sidecar. `server.ts` bootstraps schema + starter categories on first run and deliberately **ignores `DATABASE_PATH`** (Bun auto-loads stray `.env` files) in favor of `~/Library/Application Support/Sprout Account/`; override with `SPROUT_DB_PATH`. The green titlebar in `routes/shell.tsx` *is* the native window frame — drag/zoom/minimize/close are wired to Tauri.

## UI conventions

- The retro look lives in `app/app.css` as utility classes: `bevel-out`, `bevel-btn`, `bevel-in`, `field-inset`, `groove`, `titlebar`. Compose these rather than inventing new shadow stacks. Colors come from the Tailwind v4 `@theme` block (`--color-class-*`, `--color-chrome`, `--color-ledger`).
- Spending-class colors are CVD-validated and duplicated deliberately in `app/components/ui.tsx` (badges) and `app/components/charts.tsx` (`CHART_CLASS_COLORS`); keep them in sync.
- Charts are hand-rolled SVG in `app/components/charts.tsx` — there is no charting library, and adding one would fight the theme.
- UI copy is plain accounting language — accounts, transactions, categories, balances, income, expenses, transfers, backups. The retro *look* stays (Company Navigator, LCD tiles, status bar); the fantasy/adventure vocabulary was removed deliberately, so don't reintroduce quests, gold, hauls, or hoards. `routes/shell.tsx` holds the toolbar labels.
- Routes are classic loader/action modules with form posts and an `intent` field — no client-side data fetching layer.
- **Settings panes are URL state, not paths.** `?pane=accounts` (`app/lib/panes.ts`) opens a modal window over the current screen; the pathless layout `routes/settings-pane.tsx` wraps every screen, loads the pane's data, and renders `PaneWindow` beside its `<Outlet />` so the screen underneath keeps its state and scroll. `PaneWindow` is a native `<dialog>` — focus trap, inert background and focus restoration come from the platform, and Escape/✕ only *navigate*, letting the URL close the window. A pathless layout has no URL to post to, so pane writes live in their own action-only route (`routes/settings.accounts.ts`) that fetchers target by path.
- **The transaction detail window is the other kind of modal: a child route.** `/transactions/:id` is nested under `routes/transactions.tsx`, which renders it through `<Outlet />`, and the detail route itself renders the `PaneWindow` — so it has a real URL, its own loader and action, and deep links from `/transfers`, `/amazon` and the peer link still work. Two consequences to keep in mind. The register's loader now runs on every detail hit, deep links included. And because the window unmounts on close rather than staying mounted like the settings panes, the platform's focus restoration never fires — the detail route captures `document.activeElement` *during render* (`showModal()` has already moved focus by the time its effects run) and refocuses it on unmount. Register row links carry `location.search` and closing navigates back to `/transactions` + that search, so the list underneath keeps its filters and page; the same reason `intent=delete` redirects with the search string attached. The window's Previous/Next buttons walk the register's *filtered* order: `neighborTransactions` (`queries.ts`) must apply the same filters and the same `date desc, id desc` ordering as `listTransactions` — change one, change both — and it keys off the current row's date+id rather than its continued membership, because filing a category while filtered to Uncategorized drops the row from the set and Next still has to move on from where it sat.
- `CategoryCombobox` (`components/category-picker.tsx`) is the type-to-search picker used everywhere a category is chosen; it posts a hidden input exactly like the `<select>` it replaced. Its dropdown is `position: fixed` (the transaction window's scrolling body would clip an absolute one) but deliberately **not** a portal — `document.body` is outside the modal `<dialog>`, where the platform makes everything inert. `value` only seeds the selection; a caller whose server value changes underneath (the AI button) remounts it with `key`.
- **The bulk window is the third kind: neither a URL nor a child route.** Ticking rows in the register is client state (`components/bulk-categorize.tsx`, opened from the filter row), so there is no id list worth putting in the URL and nothing for a loader to fetch — the selected rows are already on the page. It posts to the action-only `api/transactions/bulk`, registered outside the `shell`/`settings-pane` layouts so a submission doesn't drag their loaders along, and the fetcher's revalidation refreshes the register underneath. Three rules the flow depends on: the selection is **per page** and resets whenever the search string changes, since a new filter or cursor is a different set of rows; counts and the posted ids are always derived as `rows.filter(selected.has)` rather than read out of the Set, because revalidation after a bulk apply drops the filed rows out of a `category=none` register and the Set would go on claiming them; and the apply clears the selection and closes the window, so a finished selection can't be applied twice. The write is a single `UPDATE … where id in (…)` — under Turso a per-row loop would be one round trip per row — with `recordUserChoice` per **distinct merchant** behind a checkbox, because that is the one side effect that outlives the rows and it overwrites memory the user can't see. No `guardLiabilityCredit` here, exactly as in `intent=update`: the guard exists to stop the memory and AI passes mis-filing, not to overrule a choice made by hand.
- The menu bar (`app/components/menubar.tsx`, contents in `routes/shell.tsx`) follows the ARIA menubar pattern. Menu entries that lead nowhere are declared `unavailable` — greyed and `aria-disabled`, not omitted.
- **The indexes on `transactions` are chosen against specific queries**, and the column order in two of them is load-bearing — `app/db/schema.ts` says which query each one serves. The rules that aren't obvious from the DDL: `txn_account_date_amount_idx` puts `id` before `amountCents` so the register's `order by date desc, id desc` stays index-ordered (reversing them costs a temp b-tree sort on every filtered page) while still covering `clearedWindows`' per-day sums; and `txn_transfer_target_idx` must stay **partial**, because almost every row's `transferAccountId` is null and a full index of mostly-null entries makes the planner scan the table instead. Measured on a 50k-row ledger, whose shape a household reaches in a few years of statements: `clearedWindows` 24ms → 5.6ms, the transfer self-join 38ms → 14ms, `accountLinkCandidates`' priors 17.5ms → 0. Three things are *not* indexable and shouldn't be chased — the register's `like %q%` search, `runMatcher`'s `like '%AMAZON%'`, and the `abs(julianday(…))` day windows — and `txn_merchant_idx` has no equality or range reader anywhere in `app/` (the register searches it with a leading-wildcard `like`, and merchant *memory* is keyed on its own table), so it is a candidate for removal that this pass deliberately left alone.
- Drizzle renders columns interpolated into `sql` templates **unqualified**, so a correlated subquery like ``sql`(select count(*) from ${transactions} where ${transactions.accountId} = ${accounts.id})` `` silently compares the inner table to itself and returns 0. Use grouped queries and join in JS instead.
